## 四、TUN 与「AI 调终端」的关系

macOS 上终端程序（`curl` / `git` / `npm` / `python requests`）**不读取系统代理设置**，
只认环境变量 `http_proxy` / `https_proxy` / `all_proxy`。

| 代理方式 | 覆盖范围 | 对 AI 调终端 |
|---|---|---|
| 系统代理 | 浏览器、读系统代理的 App | ❌ 终端命令不走代理 |
| **TUN 虚拟网卡** | **所有程序**，含终端 / Docker / 游戏 | ✅ 终端命令走代理 |
| 环境变量 | 当前 shell | ✅ 但仅限当前终端 |

**结论：为了让 AI 调用终端时能正常访问 GitHub 等外网，TUN 需要保留。**

若不想常开 TUN，可在 `~/.zshrc` 里加（`7890` 为 FlClash 的混合端口）：

```bash
export https_proxy=http://127.0.0.1:7890
export http_proxy=http://127.0.0.1:7890
export all_proxy=socks5://127.0.0.1:7890
```

## 五、YouTube 慢的排查与修复（第二轮）

### 实测数据（经代理访问 youtube.com，3 次取样）

| 次数 | TLS 握手 | TTFB | 下载速度 | 结果 |
|---|---|---|---|---|
| 1 | 2.40 s | 2.85 s | 173 KB/s | 200 成功 |
| 2 | 4.55 s | 6.02 s | 3.99 KB/s | 30 s 超时 |
| 3 | — | — | — | 连接失败 |

正常的 TLS 握手应在 0.2–0.5 s。实测 2.4–4.5 s 且抖动极大、中途直接失败，
说明线路质量确实有问题，不是错觉。

> 注：TUN 模式下不能用 TCP 握手测节点延迟 —— 内核会乐观应答，
> 测试中连必然不可达的 `192.0.2.1` 都返回"成功 0 ms"。

### 根因（两个问题叠加）

**1. YouTube 走的组里没有专线节点**

`youtube.com` / `googlevideo.com` / `ytimg.com` 等全部命中 `🎯 Google` 组。
该组原本只有两个成员：「🇯🇵 日本优选」和「🇯🇵 日本稳定」，
**hysteria2 流媒体专线（🇯🇵 日本专线，4 条）根本没有被挂进来**。

**2. 当前选的是 fallback 类型组 —— 这是最坑的地方**

「🇯🇵 日本稳定」是 `fallback` 类型：逻辑是**取列表里第一个"能连上"的节点，然后一直用**，
**不比较速度**。只要排第一的「🇯🇵日本高速01|BGP|CUCM」（node-xxx.example.com）能建立连接，
哪怕它慢到 4 KB/s，fallback 也**永远不会**自动切到更快的线路。

对比：「🇯🇵 日本优选」是 `url-test` 类型，每 180 秒自动测速选最快，
且其测速地址正是 `https://www.gstatic.com/generate_204`（Google 自己的域名），
测出的延迟直接反映访问 Google / YouTube 的真实质量。

### 另一个发现：节点存在大量地址复用

51 个节点里很多"不同名字"其实指向**同一台服务器**：

| 服务器地址 | 复用它的节点 |
|---|---|
| `cfyes.7770006.xyz:443` | 日本高速 01、02、06、07、08、09（6 个） |

| `cfyes.777078.xyz:443` | 美国高速 01–05、英国伦敦 01（6 个） |

这些"不同节点"是同一根管子，测速差异只是抖动，**不构成真正的冗余**。
真正独立的是 `aws-link*.节点域名` 系列和 hysteria2 专线。

**被限速的流媒体节点**或**高倍率节点**来跑普通流量，既不快也不省流量。

|---|---|---|

| `mixed` | TCP 走 system，UDP 走 gvisor | 兼顾性能与 UDP 兼容性，最推荐 |
| `gvisor` | 纯用户态栈，CPU 开销高 | 兼容性兜底 |

你的配置里写的是 `stack: "mips"`（非标准值），可能是 FlClash 的内部标识。
**建议到 FlClash 的 TUN 设置里看一眼「栈 / Stack」选项**，如果能选，
改成 **Mixed** 对吞吐更友好（大流量下载尤其明显）。

## 七、实测结论：节点侧全面不可用（22:12 复测）

### 跨线路组对比测试

| 目标 | 走哪个组 | 结果 |
|---|---|---|
| `google.com/generate_204` | 🎯 Google（日本稳定） | ✗ 超时 5.0 s |
| `api.telegram.org` | ✈️ Telegram（日本优选） | ✗ 超时 5.0 s |
| `api.openai.com` | 🤖 AI（美国优选） | ✗ 超时 5.0 s |
| `youtube.com` | 🎯 Google（日本稳定） | ✗ 超时 5.0 s |
| **`github.com`（对照组）** | **未匹配 → 直连** | **✓ 正常，0.98 s** |

### 判读

**直连对照组正常** → 本机网络、TUN 虚拟网卡、代理端口 7890 全部健康，
排除了"你电脑的问题"。

**所有代理线路组同时失败** → 问题出在节点侧。
不是某一个节点坏了，而是**换哪个组都一样**。

**每次失败都精确卡在 5.000 秒** → 这是内核（mihomo）连接节点服务器的
dial 超时。意味着**连 TCP 都建立不起来**，性质是"连不上"，不是"慢"。

**但 22:01 与 22:11 的测试各有 1 次成功**（TLS 0.31 s / 173 KB/s），
说明节点是**间歇性可用** —— 典型的高峰期链路拥堵 / 被限速特征。

### 最需要做的一件事：更新订阅

你的配置是**本地静态文件，不带订阅地址**：

```
profiles 表：label = FLClashmac-内嵌稳定.yaml
             url  = （空）
             auto_update = 1
```

`url` 为空意味着 **FlClash 无法自动更新节点**。机场为避免被封会定期更换
节点地址，一旦更换，这份本地配置里的地址就会全部失效 ——
这很可能就是当前全线不通的根本原因。

**处理方式**：到机场官网 / 用户群获取**最新的订阅链接**，
在 FlClash 里走「配置 → 添加 → 从 URL 导入」，替换掉现在这个本地文件。
换成 URL 订阅后节点地址会随订阅自动更新，以后不会再出现这类问题。

> 建议顺序：**① 先完全重启一次 FlClash**（顺便让本次配置优化生效）→
> **② 用 `FlClash-测速.sh` 复测** → **③ 仍不通就更新订阅** →
> **④ 还不行就是机场线路问题，直接联系机场**。

# 十、「测速数字飘忽 / 显示断线」的修正（2026-10-15）

## 10.1 先回答：能不能直接写在 yaml 里

**能，但要分清两套东西 —— 它们不在同一个地方。**

| 测速入口 | 参数存在哪 | 能否用 yaml 改 | 结果 |
|---|---|---|---|
| **策略组自动健康检查**（`♻️ 自动选择`、`🇯🇵 日本优选`… 每 N 秒自己测一遍） | **profile 文件**（就是 yaml） | ✅ 能 | 已改 |
| **界面上点「测延迟」** 那个按钮 | FlClash **App 设置**（plist 里的 `appSettingProps.testUrl`） | ❌ 不在 yaml 里 | 需在 App 设置里改一次 |

也就是说：**自动那部分已经全部落到 yaml 里了**；手动点按钮那部分用的一直是 App 自带设置（当前是 `https://www.gstatic.com/generate_204`），yaml 管不到它。

另一件重要的事（本轮实测确认）：
**FlClash 每次启动都会用 profile 重新生成 `config.yaml`。**
证据：10-15 16:57 App 重启后 `config.yaml` 被重写（时间戳变了），但里面第九节的改动（`include-all-proxies`、伪节点已删、Apple 直连段）全在 —— 说明这些改动存活的原因是**它们在 profile 里**。
→ 所以结论是：**改 profile 才持久，改 `config.yaml` 只是让当前这份文件一致**（本次两个文件都改了）。

## 10.2 改了什么（12 个测速组，两个文件同步）

| 参数 | 改前 | 改后 | 为什么 |
|---|---|---|---|
| `url` | `https://www.gstatic.com/generate_204` | **`http://cp.cloudflare.com/generate_204`** | 去掉 TLS 环节，少 2 个跨境往返；TLS 握手本身就是「偶发失败」的主要来源；Cloudflare 是 anycast，节点就近响应 |
| `lazy` | `true` | **`false`** | 默认「有流量时不重测」。你挂着 YouTube，组里选中的死节点就永远不会被换掉。关掉后按间隔强制重测 |
| `interval` | 180 | **300** | 配合 `lazy:false`：既要定期重测，又不要测太勤影响正常上网 |
| `timeout` | 5000 | **8000** | 晚高峰节点握手普遍变慢，5 秒会大量误判成「断线」 |
| `expected-status` | 无 | **204** | 明确要求 204，避免节点返回干扰页/302 被算作成功 |
| `max-failed-times` | 无 | **3** | 连续 3 次失败才判死，避免单次抖动就切走 |

`tolerance` 保持原样（自动选择 50ms，其余 30ms）——这是「避免在噪声里反复横跳」的阈值，不动。

## 10.3 新增：真实带宽测试通道

yaml 里加了两样东西（这是延迟测试做不到、但判断节点好坏最需要的能力）：

```yaml
- name: 🧪 节点测速          # 选择组，默认 DIRECT
  type: select
  include-all-proxies: true
  proxies:
  - DIRECT
```
```yaml
# 规则段第 0.6 段，位于 Apple 直连段之后
- 'DOMAIN-SUFFIX,speed.cloudflare.com,🧪 节点测速'
```

原理：脚本把 `🧪 节点测速` 逐个切到目标节点，然后从 `speed.cloudflare.com` 拉 10MB 实测**真实下行带宽**，测完切回 DIRECT。
平时这个组停在 `DIRECT`，只有脚本会动它，不影响任何正常流量。


真正有变化的只有「启动那一刻」：+0.25 秒（一次性），常驻内存没有可测量增长。

## 14.2 实测数据（标准 mihomo v1.19.11 内核，同一台机器）

| 配置 | 规则数 | 启动就绪 | 常驻内存 | 单次请求中位（百度，n=15） |
|---|---|---|---|---|
| 扩容前 | 140 | 0.22 s | 157.0 MB | 58.6 ms |

| 压力测试 A | 2,140 | 0.31 s | 155.9 MB | — |

- 内存数字在 145–157 MB 之间抖动，是测量噪声（同一条配置重跑也会差 10 MB），**不是"规则多了反而更省内存"**。
- 规则数加一万条，**启动时间没有任何变化**，说明瓶颈不在规则条数，而在加载 geosite 数据集那一下。

## 14.3 为什么不会卡

| 机制 | 成本 |
|---|---|
| `DOMAIN-SUFFIX` / `DOMAIN` | 内核把域名倒序建成字典树（trie）。匹配只跟**域名长度**有关，跟规则条数无关 → 微秒级 |
| `GEOSITE` | 整包编译成同样的 trie，命中同样是微秒级。1 万条记录占十几 MB 内存 |
| `IP-CIDR` | 二进制 trie，同样与条数无关 |
| `DOMAIN-KEYWORD` | 唯一需要逐条字符串比对的类型 —— **本次一条都没加** |

规则列表是"命中即停"的线性扫描，但每一跳只是一次哈希/树查找（纳秒级），不是字符串遍历。所以第 700 条规则和第 7 条的代价一样。

## 14.4 真正会拖慢的写法（这次全部避开了）

| 写法 | 代价 | 本次是否使用 |
|---|---|---|
| `GEOIP` 不写 `no-resolve` | 每个未命中的域名都要先做一次真实 DNS → 几十到几百 ms | ❌ 已有规则带 `no-resolve` |
| 大量 `DOMAIN-KEYWORD` | 纯字符串包含匹配，越多越慢 | ❌ 0 条 |
| `RULE-SET` 远程订阅 | 启动/更新时要下载并解析大文件，体感明显卡 | ❌ 未用 |
| 定时重载配置 | 每次重载 ≈ 0.4 s 卡顿 | 仅启动时一次 |
